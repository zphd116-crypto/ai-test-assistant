• 发 HTTP 请求

• 读写数据库

没有 Schema → LLM 不知道有什么工具 → 永远不会调用 Function

模块二 · 必须知道的 4 个反常识

12 / 20

⚠️ 4 个 反常识 认知点

99% 的人第一次接触 FC 都会理解错的地方

①

LLM 根本不执行函数！

很多人以为是 LLM 自己去调 API → ❌ 错！LLM 只是"建议你调用某个函数"。

类比：LLM 是开处方的医生，你的代码才是配药、给药的护士
②

description 比工具本身更重要

LLM 怎么知道有什么工具？靠你给它的"工具描述"。描述写得越好，AI 调用越准。

测试同学的优势：写好工具描述 = 写好用例 description
③

LLM 会"主动反问"

如果工具需要"城市"参数，但用户没说，LLM 会回："请问您想查哪个城市？"——不会瞎编参数。

类似一个有责任心的实习生，缺信息会主动找你确认
④

安全完全可控

因为执行权在你的代码里，所以你可以：拒绝危险调用、修改参数、加权限校验、加审计日志。

例：禁止 AI 调"删库"SQL，只允许 SELECT

模块二 · 写好 Schema 的黄金法则

13 / 20

5 条 黄金法则

让你的 Agent 智商提升 80%

1

Description 越清楚，调用越准确

用业务语言描述，不要用技术黑话

2

参数命名要直观

order_id 优于 id

3

善用 enum 限制取值

避免 LLM 自由发挥，比如 method 只能是 GET/POST/PUT/DELETE

4

必填 vs 可选要严格区分

required 字段不写，LLM 就会瞎填

5

错误返回要结构化

让 LLM 能理解错误原因并自我纠正

范例：一个写得好的 Schema

{
  "name": "http_request",
  "description": "向被测 HTTP 接口发起请求
    支持 GET/POST/PUT/DELETE 方法
    用于执行接口测试",
  "parameters": {
    "type": "object",
    "properties": {
      "method": {
        "type": "string",
        "enum": ["GET","POST","PUT","DELETE"],
        "description": "HTTP 方法"
      },
      "url": {
        "type": "string",
        "description": "完整的接口 URL"
      },
      "body": {
        "type": "object",
        "description": "请求体，仅 POST/PUT 需要"
      }
    },
    "required": ["method", "url"]
  }
}
✓ 业务化描述 ✓ 命名清晰 ✓ 用 enum ✓ required 明确
